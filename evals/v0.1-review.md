# v0.1 Forward Review

Method: manually simulate the intended response structure for all seven cases, then score against `rubric.md`. This is an instruction-level forward review, not an independent model run. It is useful for catching obvious routing and instruction defects; future maintenance should add blind model runs when behavior in real use is inconsistent.

## Observed failure modes

### Repetitive evidence labels

In the technical root-cause case, almost every candidate cause had the same status because the prompt contained no measurements. Applying the four evidence labels literally would add ceremony without discrimination.

**v0.2 correction:** use status labels only when they reveal meaningful differences. Otherwise state the common evidence gap once and prioritize candidates by probability and decision relevance.

### Unranked dissatisfaction lenses

In the dissatisfaction case, the instruction to offer a few candidate diagnoses could still yield an evenly weighted menu such as framing, time horizon, and objective function. That makes the user do the synthesis and can feel like another generic framework.

**v0.2 correction:** lead with the strongest diagnosis and cite the cue supporting it, then give only the most plausible alternative(s).

## Instructions deliberately not added

- No mandatory response template: it would make simple cases mechanical.
- No fixed number of hypotheses: the right number depends on the decision.
- No requirement to ask a clarifying question: clarification is useful only when it changes the next move.
- No exhaustive strategy checklist in the core file: the diagnostic lenses are conditional reference material.
- No scripts or external dependencies: this skill changes reasoning behavior and has no deterministic transformation to automate.
